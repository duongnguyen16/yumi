# WDP-31 and WDP-32 End-to-End Design

## Goal

Implement the canonical ownership dispute and appeal flows from backend to frontend while limiting changes to behavior required by WDP-31 and WDP-32.

## Source of truth

Priority is `docs/CONTEXT.md`, then the current schemas and live module contracts, then the implementation guide. The older WDP-31 and WDP-32 guidelines are not implementation sources when they conflict with those contracts.

## Scope

### WDP-31

- Open an ownership dispute only after a rejected RequestAccess appeal is accepted.
- Let both dispute parties view the case and add evidence while it is open.
- Provide an Admin queue and detail view.
- Resolve with KEEP, TRANSFER, or REVOKE.
- Keep the current owner for KEEP.
- Transfer to the requester for TRANSFER without enabling ownership hold.
- Remove the owner for REVOKE so the normal claim flow becomes available again.
- Notify both parties and write an audit record.
- Provide Admin Web screens and Vendor Mobile screens required by this flow.

### WDP-32

- Submit an appeal with an argument and at least one additional evidence file.
- Allow one appeal per original decision within 14 days.
- Keep the adverse state unchanged while the appeal is pending.
- Prevent the original Admin from reviewing their own decision when the original decision came from an Admin.
- Accept a rejected RequestAccess appeal into a dispute.
- Overturn or uphold supported Admin decisions using the current target schemas and audit history.
- Notify the appellant and write an audit record.
- Provide an Admin Web queue/detail flow and reusable Vendor Mobile appeal screens.

## Explicit non-goals

- No refactor of Report, User management, Trust Engine, or Notification infrastructure.
- No new trust score rules for disputes or appeals.
- No cron job.
- No duplicate merge implementation.
- No changes to unrelated task screens solely to add appeal buttons.
- No branch change, commit, or push.

## Data contracts

### Dispute

`Dispute` gains an optional indexed `requestAccessId`. New disputes created by WDP-32 require this source. A partial unique index prevents more than one dispute for the same RequestAccess while preserving compatibility with existing data.

The current `vendorAId`, `vendorBId`, `evidenceA`, `evidenceB`, `status`, and `adminDecision` fields remain. Vendor A is the owner recorded on RequestAccess. Vendor B is the requester.

### Appeal

`Appeal` gains `argument`, `originalDeciderId`, and `originalDecidedAt`. The original decision snapshot avoids changing behavior when the source record changes later.

`AppealType` gains `REQUEST_ACCESS_REJECTED`. `AppealStatus` gains `ACCEPTED_TO_DISPUTE` for the special RequestAccess branch. Existing appeal types remain supported through restoration handlers without changing their source modules.

The unique key remains the original decision identity represented by `targetCollection` and `targetId`.

## Backend behavior

### Appeal submission

The service maps each AppealType to its current collection and verifies:

- the target exists and is in an appealable adverse state;
- the authenticated user is the affected user;
- the original decision is within 14 days;
- no appeal already exists for that decision;
- an argument and at least one evidence file are present.

Submission creates a PENDING appeal and does not modify the source target.

### Appeal resolution

For an Admin-originated decision, the resolver must differ from `originalDeciderId` when that value exists.

UPHELD closes the appeal without changing the target.

OVERTURNED delegates to a focused restoration service:

- location request: restore the request for approval and publish its location;
- claim request: return the rejected claim to PENDING without assigning ownership;
- duplicate location: restore PUBLISHED and clear the duplicate flag;
- ownership revoke: restore the prior owner from the original audit diff;
- removed review: restore PUBLISHED;
- banned user: reuse `TrustEngineService.unbanUser`, then restore the previous status from the original audit diff;
- warned user: restore the previous status from the original audit diff without running unban.

For REQUEST_ACCESS_REJECTED, the accepted outcome is ACCEPTED_TO_DISPUTE rather than OVERTURNED. It atomically changes RequestAccess from REJECTED to ESCALATED and creates one OPEN Dispute sourced from that request.

### Dispute participation

Authenticated Vendor A and Vendor B can view their dispute. While the dispute is OPEN, each party can add evidence only to their own evidence list. Admin endpoints expose the queue and full case detail.

### Dispute resolution

The outcome fully determines ownership:

- KEEP preserves Vendor A as owner.
- TRANSFER sets Vendor B as owner and clears any stale hold value.
- REVOKE clears owner and hold.

The service rejects a closed dispute, a missing location, or a location whose current ownership no longer matches the case assumptions. Every successful resolution stores `adminDecision`, notifies A and B, and writes an audit diff containing the previous and next owner IDs.

## Frontend behavior

### Admin Web

Add navigation entries and pages for:

- Disputes: queue, evidence comparison, location and party information, KEEP/TRANSFER/REVOKE action with a required reason.
- Appeals: queue, original decision summary, new evidence, UPHELD/OVERTURNED actions, and ACCEPTED_TO_DISPUTE for RequestAccess appeals.

The pages reuse current Admin layout, cards, drawers, action buttons, tokens, loading states, and API client conventions.

### Vendor Mobile

The RequestAccess detail screen shows an appeal action only for the rejected requester within the permitted window. A reusable appeal screen collects the argument and evidence. Appeal detail displays status and the linked dispute when accepted.

A dispute detail screen lets Vendor A and Vendor B review both evidence sets and add evidence to their own side while the case is open.

## Error handling

Services return the existing `{ success, statusCode, message }` shape. Controllers map 400, 403, 404, 409, 410, and 422 consistently. Duplicate-key errors are converted to 409. Frontends display server messages and prevent repeated submissions while requests are pending.

## Testing

Use test-first development for:

- appeal authorization, required evidence, duplicate decision, and 14-day expiry;
- original Admin separation;
- pending adverse state preservation;
- rejected RequestAccess to ESCALATED plus exactly one Dispute;
- each supported restore handler;
- dispute source, participant evidence permissions, all three outcomes, audit, notification, and no-hold invariant;
- API clients and critical frontend states where the current test setup supports them.

Verification includes focused tests, full API tests, API build, Web lint/build, Mobile typecheck, and a final Git diff review. No commit is created.
